## C++20 协程

### 一、理解整体的框架

协程其实是"可以暂停的函数"

普通函数一旦调用，就一口气跑到 return，栈帧（stack frame）用完就销毁    //栈帧：返回地址、局部变量（不一定全部存放在栈上）、保存的寄存器、临时数据、函数参数

协程（coroutine）不一样：它可以在中途挂起（suspend），把执行权交还给调用者，之后再从挂起点原地恢复（resume），局部变量还活着。

普通函数的局部变量在栈上，函数一返回栈帧就没了。那协程挂起后，它的局部变量、"下次从哪一行继续"这些状态存哪儿？

答案是：编译器把这些状态打包进一个堆上分配的对象，叫 coroutine frame（协程帧）。这个帧里大致有：

- 挂起时所有需要保活的局部变量
- 一个"恢复点"索引（resume index，即下次从哪继续）
- 一个指向 resume 函数 和 destroy 函数 的指针
- promise 对象

> 🔑和论文的连接：这篇论文攻击的核心，就是这个堆上的 coroutine frame 里存着函数指针（resume/destroy）。如果攻击者能篡改这个帧，让 resume 指针指向别处，调用 handle.resume() 时就跳到攻击者想去的地方——而且这跳转通常"绕过"了传统 CFI 的检查。

我们通过使用这些关键字让编译器当作协程处理，而不是普通函数

- `co_await` —— 挂起，等待某个东西
- `co_yield` —— 产出一个值并挂起（常用于生成器）
- `co_return` —— 协程版的 return

理解两个问题

**Q1：为什么协程帧必须放在堆上，而不能像普通函数那样放栈上？**

A1：本质的原因是生命周期不匹配：协程挂起后，创建它的那个栈帧可能早就返回销毁了，但协程的状态还得活着等 resume。栈的 LIFO 决定了它扛不住这种"创建者先走、被创建者后活"的错位，只有堆能托管这种独立生命周期。

**Q2：既然帧里存着 resume 函数指针，那论文"劫持协程"是在劫持什么?**

A2:劫持的是 coroutine frame 里那个 resume 指针（有时是 destroy 指针）.

### 二、理解协程里汇编的调用

#### 1. coroutine_handle<> —— 协程帧的"遥控器"

本质就是一个指向堆上 coroutine frame 的指针，包了层壳。拿到它就能：

```cpp
h.resume();    // 或写成 h()，从挂起点恢复执行
h.destroy();   // 销毁协程帧，释放堆内存
h.done();      // 是否已执行完
```

> 🔑 论文连接：h.resume() 在汇编层面，就是去 frame 里取出 resume 函数指针然后 call/jmp 过去。攻击者改掉 frame 里那个指针，h.resume() 就成了"受控跳转"。这就是"hijacking C++ coroutines"字面的意思。

#### 2. promise_type —— 协程的"控制面板"

每个协程类型内部必须定义一个 promise_type，它规定了这个协程的行为策略。编译器会在协程帧里放一个 promise 对象，并在固定时机回调它的成员函数：

```cpp
struct promise_type {
    MyCoro get_return_object();        // 怎么造返回给调用者的对象
    std::suspend_always initial_suspend(); // 一开始就挂起？还是立刻跑？
    std::suspend_always final_suspend() noexcept; // 结束时挂起？
    void return_value(int v);          // co_return v 时调用
    // 或 void return_void();          // co_return; 时调用
    std::suspend_always yield_value(int v); // co_yield v 时调用
    void unhandled_exception();
};
```

可以把 promise_type 理解成："当协程发生 X 事件时，该怎么办"的一张回调表。这些回调返回的那些 suspend_always / suspend_never，就是下一个主角——awaiter。

#### 3. awaiter —— 决定"这次 co_await 到底挂不挂、挂了去哪"

```cpp
struct Awaiter {
    bool await_ready();
    //   返回 true  → 不挂起，直接往下跑（省掉一次挂起开销）
    //   返回 false → 真的挂起，进入下面一步

    auto await_suspend(coroutine_handle<> h);
    //   挂起的瞬间调用，参数 h 就是当前协程的句柄。
    //   你可以在这里把 h 存起来（比如交给调度器/事件循环，等事件好了再 h.resume()）
    //   返回类型决定接下来把 CPU 交给谁。

    T await_resume();
    //   恢复后调用，它的返回值就是整个 co_await 表达式的值。
};
```

执行顺序:查看是否ready，否：suspend（交出控制权）

综上：协程把"下次跳哪"这件事，从栈上的返回地址，搬到了堆上 frame 里的 resume/destroy 函数指针。栈上返回地址有现代防护，而堆上这俩指针——攻击者改了它，再诱发一次合法的 h.resume()，控制流就被劫持，且 CFI 常常拦不住。这就是整篇论文的靶心。

## x86_64 底层

栈帧、返回地址、call/ret、GOT/PLT

### 1. ROP的秘密：call和ret在做什么

call target 做两件事：

1. 把下一条指令的地址（返回地址）压栈：push 返回地址（rsp 减 8）
2. 跳过去：rip = target

ret 做一件事：

从栈顶弹出一个地址，跳过去：rip = pop()（rsp 加 8）

正如我们学过的：ret其实不管栈顶8字节的是什么，无脑相信的

> 🔑 论文/ROP 连接：如果攻击者能往栈上写（典型的栈溢出），把"返回地址"改成任意值，那个函数 ret 时就跳到攻击者指定的地方。这就是返回地址劫持，是 ROP 的起点。模块四讲的"影子栈（shadow stack）"正是为了保护这 8 字节不被改。

### 2. 栈帧的结构

假设有一个函数greet被调用

```text
高地址
       ...                      <- main 的栈帧
       [返回地址 = 0x1170]       <- call greet 压入的，greet 的 ret 会跳回这里
rbp -> [greet 保存的旧 rbp]      <- greet 里 "push rbp" 压入
       ...                      <- greet 的局部变量区
rsp -> ...
低地址
```

函数序言（prologue）：

```asm
push rbp        ; 保存调用者的 rbp
mov  rbp, rsp   ; 用 rbp 锚定本帧基准
```

尾声（epilogue）：

```asm
pop rbp 恢复
ret 弹返回地址跳回
```

### 3. GOT / PLT——程序怎么调用 libc 里的 system/puts

PLT 是代码里的跳板，GOT 是数据里的地址表；桩从 GOT 读地址跳转

PLT（Procedure Linkage Table）：代码段里的一小段"跳板桩"。通过 call puts@plt，跳到这个桩。

GOT（Global Offset Table）：数据段里的一张函数地址表。桩再从 GOT 里读出真实地址跳过去。

> 🔑 两个经典攻击面，模块三会用：
>
> GOT 覆写：GOT 是可写数据（没开 Full RELRO 时）。改掉 puts 的 GOT 槽为 system 的地址，之后程序以为在调 puts("/bin/sh")，实际执行 system("/bin/sh")。
>
> 泄露 libc 基址：读出某个 GOT 槽里的真实地址，减去已知偏移，就反推出整个 libc 的加载基址——于是 ASLR 被绕过，system、/bin/sh 的地址全有了。这正是 ret2libc 的套路。

疑问

**Q：为什么说"泄露一个 GOT 槽的值"就能打穿 ASLR？**

A：关键在于 libc 是"整块"加载的。ASLR 每次把 libc 随机放到某个基址，但 libc 内部各函数之间的相对偏移是固定的（同一个 libc 文件，编译好就定死了）。所以：

```text
puts 真实地址  =  libc基址 + puts的固定偏移
system 真实地址 =  libc基址 + system的固定偏移
```

GOT 槽里存的正是运行时填好的真实地址（模块二看到的）。攻击者用一个"读"漏洞读出 puts 的 GOT 槽 → 得到 puts 真实地址 → 减去 puts 的已知偏移 → 反推出 libc 基址 → 再加 system/"/bin/sh" 的偏移，整个 libc 里任何东西的地址都算得出。ASLR 随机的只是"这一块整体挪到哪"，泄露一个点就把整块定位了。一句话：ASLR 随机的是基址，不是内部布局；漏一个绝对地址 = 漏整个基址。

## 代码复用攻击谱系

### 第 1 讲——为什么要"复用代码"

#### 1. 先理解防御方先出的招：W^X / DEP（Write XOR eXecute，又名 DEP/NX）

内存要么可写、要么可执行，不能既可写又可执行

- 栈、堆（可写）→ 不可执行。塞进去的 shellcode 是数据，CPU 拒绝执行它。
- 代码段（可执行）→ 不可写。改不了现成代码。

防止了shellcode类型的攻击

#### 2. 第一步进化：ret2libc "return to libc"

既然不能自己写代码，那就借现成的函数。程序大多链接了 libc，里面有 system()。攻击思路：

1. 栈溢出改返回地址 → 指向 libc 里 system 的入口
2. 按调用约定（模块二！）把参数 "/bin/sh" 的地址摆进 rdi
3. 函数 ret 时就"返回"到了 system，等于执行 system("/bin/sh")，拿到 shell

前面提到的GOT 泄露打穿 ASLR，我们可以轻易的算出system 和 "/bin/sh" 的地址

局限：一次基本只能调一个（或少数几个）完整函数，表达能力有限。攻击者想要"图灵完备、能拼出任意逻辑"的能力——于是进化到 ROP。

整个攻击的发展：

```text
注入 shellcode  --被 W^X 封杀-->  复用现成代码
   ret2libc（借整个函数）  --表达力不足-->  ROP（借指令碎片，任意拼装）
   ROP（靠 ret/栈）  --被影子栈等打击-->  JOP（改靠 jmp/call）
   碎片式(ROP/JOP)  --面对C++/CFI-->  COOP（复用整个虚函数，像"正常"调用）
```

**Q:ret2libc 为什么不违反 W^X？（它执行的代码在哪个内存区？）**

A:栈上放的只有数据：伪造的返回地址和参数，比如 "/bin/sh" 的地址。

真正执行的 system() 是 libc 里本来就有的合法机器码。它所在的页是可执行、不可写的，所以 W^X 完全不拦它。

### 第 2 讲——ROP 与 JOP 的机制

#### 1. Gadget：以 ret 结尾的"指令碎片"

ret2libc 一次只能借一个完整函数，表达力不够。

ROP（Return-Oriented Programming）

不借整个函数，而是借函数中间的一小段指令，只要这段指令以 ret 结尾。这样的碎片叫 gadget。

程序和 libc 里这种碎片很多，例如：

```asm
pop rdi        ; 从栈顶弹一个值进 rdi
ret            ; 再弹下一个地址并跳过去
```

这个 gadget 的作用是"把栈上的下一个值装进 rdi"。模块二讲过，rdi 是第 1 个参数，所以它就是"设置第一个参数"的工具。

#### 2. 链接：ret 自动把碎片串起来

ret 的行为是"弹栈顶地址并跳过去"。所以攻击者在栈上摆一排地址，每个 gadget 执行完一个 ret，就自动跳到栈上的下一个地址。

举一个system("/bin/sh")的例子

```text
栈顶 →  [ gadget: pop rdi ; ret 的地址 ]   ← 被改写的返回地址
        [ "/bin/sh" 字符串的地址        ]   ← 被 pop rdi 弹进 rdi
        [ system 的地址                 ]   ← pop rdi 后的 ret 跳到这里
```

执行顺序：函数返回时跳到 pop rdi; ret，把 "/bin/sh" 地址装进 rdi，随后 ret 跳到 system，参数正好在 rdi 里。栈上全是地址和数据，没有一个字节的新机器码，所以 W^X 防不住

把足够多的 gadget 组合起来，就可以形成一个完整的攻击链。这就是 ROP 比 ret2libc 强的地方。

> 🔑 对应到防御：ROP 的命脉是"栈上的返回地址被篡改 + ret 无脑信任它"。影子栈（模块四）就是在 ret 时拿真实返回地址和另存的副本比对。

#### 3. JOP：把 ret 换成间接 jmp

既然防御盯着 ret，攻击者就换一种"连接方式"。JOP（Jump-Oriented Programming）里的 gadget 以间接跳转结尾，比如 jmp rax 或 call rbx，而不是 ret。

思考：ret自带"栈顶取下一个地址"的功能，jmp没有，怎么办？

JOP 的答案是用一个调度器 gadget（dispatcher）：

- 在一张攻击者控制的"调度表"里存一串 gadget 地址
- 用一个寄存器当"程序计数器"，每执行完一个 gadget 就推进它，再 jmp 到表里的下一项

（我在PWN的解题目前还没有接触过，先记住）

结构上等于自己搭了一个小虚拟机。思想没变（复用现成碎片），区别是控制流不再依赖栈上返回地址，所以不受"只保护返回地址"的防御限制。

#### 4. 为什么这条线最后会走向 COOP 和这篇论文

ROP/JOP 的 gadget 往往落在函数中间，或者落点本来就不是正常的调用目标。CFI 正是抓这个特征：间接 call/jmp/ret 的目标必须是"合法目标"，gadget 落在函数中间就被拦下。

于是攻击者要找"落点本身就合法"的复用方式，COOP 就是这条路的第一个答案。

### 第 3 讲——COOP：只复用"完整的虚函数"

#### 1. 先补 C++ 虚函数的底层，这是 COOP 的地基

C++ 里带 virtual 的类，每个对象开头有一个隐藏指针 vptr，指向这个类的 vtable（虚函数表，一排函数指针）。调用 obj->foo() 的汇编大致是：

```asm
mov rax, [rdi]        ; rax = obj 的 vptr
mov rax, [rax+0x10]   ; rax = vtable 里第 N 项（foo 的地址）
call rax              ; 间接调用
```

这和模块一里 h.resume() 的 mov rdx,[rax]; call rdx 是同一个形状，都是"从内存里读函数指针再间接调用"。区别在于 vtable 在只读段，而协程 frame 在堆上。

#### 2. COOP 的思路（Counterfeit Object-Oriented Programming）（伪造面向对象编程）

COOP 的出发点是：ROP/JOP 的 gadget 落在函数中间，会被 CFI 抓到。那就只用完整的虚函数当 gadget，并且让每一次调用都像一次正常的虚调用。

- gadget = 一个完整的虚函数，叫 vfgadget。它从函数入口开始，正常 ret 返回，落点是合法的函数入口。
- 调度器 = 一个主循环 gadget，叫 ML-gadget（main loop）。它通常是程序里某个"遍历对象数组并依次调用每个对象的虚函数"的循环，比如 for (obj : objs) obj->foo();。

攻击者在堆上伪造一批对象，每个对象的 vptr 指向自己挑好的 vtable。ML-gadget 循环时就按顺序调用这些伪造对象的虚函数，于是一个个 vfgadget 被串起来执行。

vfgadget 之间靠共享的数据传值：前一个函数把结果写进某个对象的字段，后一个函数从那里读。

| | gadget | 串联 | 落点特征 |
| --- | --- | --- | --- |
| ROP | 函数中间的碎片 | ret + 栈 | 函数中间 |
| JOP | 函数中间的碎片 | 间接 jmp + 调度器 | 函数中间 |
| COOP | 完整虚函数 | 主循环里的虚调用 | 函数入口，且像正常虚调用 |

虽然目前这个笔记主要是在讲学术论文讨论的抽象机制层面，没有展开学习可执行的利用步骤

对于“攻击者在堆上伪造一批对象，每个对象的 vptr 指向自己挑好的 vtable。”有点好奇，怎么直接略过了，然后了解到COOP 研究的不是"怎么获得写堆能力"，而是"已经有任意写/堆溢出/UAF 这类原语之后，怎么把它变成完整的控制流劫持"。所以这步的起点是：攻击者通过某个内存破坏漏洞，能把任意字节写到堆上某个自己控制的位置。这是一切后续讨论的假设前提。

概念上：vptr 只是内存里的一个指针值

C++ 对象在内存里的布局是固定的——头 8 字节就是 vptr，后面跟着成员变量，这是 ABI 规定的，不是运行时才决定的秘密。所以"伪造对象"概念上就是：

1. 攻击者事先通过读符号表或已泄露的信息，知道某个真实存在的类的 vtable 在内存里的地址（这又依赖前面讲过的"泄露一个地址反推整个模块基址"那套技巧）。
2. 用已有的写原语，在堆上某块可控内存的头 8 字节，写入这个已知的、真实的 vtable 地址。
3. 再找到一个会把这块内存当"某个带虚函数的对象"来使用、并发起虚调用的位置（即前面讲的 ML-gadget）。

这里为后面留下一个伏笔：为什么没有检查这个虚函数是不是合法函数

## CFI 基础

### 第 1 讲 ————原始 CFI 的想法，以及粗/细粒度之分

CFI（Control-Flow Integrity，控制流完整性）是防御方对前面所有攻击的正面回应。

理解论文的一条核心论证：为什么现有防御挡不住协程劫持

#### 1. CFI 想解决的问题

编译器可以为程序画出一张"控制流图"（CFG，Control-Flow Graph）：哪个函数能调用哪个函数、哪个间接跳转合法地跳到哪些目标，这些在编译期基本是确定的。CFI 的想法是：在每一次间接跳转（间接 call、间接 jmp、ret）发生前，检查这次跳转的目标是不是 CFG 里允许的，不允许就终止程序。

> 在计算机中，一个程序从我们编写源代码，到最终由 CPU 执行，需要经过一系列步骤：
>
> 预处理 → 编译 → 汇编 → 链接 → 装载 → 执行 → 退出。

直接调用（call 固定地址）不需要检查，因为目标写死在代码里，攻击者改不了。需要检查的只有三类：

- 间接 call（函数指针、虚函数调用）
- 间接 jmp（switch 跳转表、JOP 用的那种）
- ret（目标来自栈，ROP 利用的就是它）

#### 2. 原始 CFI 的实现方式：标签 + 运行时检查

- 编译期给每个合法的跳转目标打上一个标签（label），比如在函数入口前插入一条特殊标记指令。
- 每个间接跳转点也编译期确定"这里允许跳到哪些标签"。
- 运行时，每次间接跳转前先插入一段检查代码：读目标地址处的标签，看它是否在"这个跳转点允许的标签集合"里，不在就 abort。

ROP/JOP：  gadget 落在函数中间，中间位置没有合法标签，检查不通过。

#### 3. 粗粒度 vs 细粒度：标签集合"认得多细"

粗粒度 CFI（coarse-grained）：标签集合很宽松，比如"所有间接 call 只要落在任意函数的入口就算合法"，不区分调用点的类型、不区分目标函数签名。性能开销小，但允许的目标集合大，COOP 这类攻击专挑"落在合法入口但类型不对"的目标，粗粒度 CFI 拦不住。

细粒度 CFI（fine-grained）：标签按调用点的上下文精确划分，比如"这个调用点只能调用某个特定基类及其子类里签名匹配的虚函数"。安全性强得多，但要做到完全精确需要精确的类型信息和调用图分析，实现开销大，现实中工业界部署的大多是粗粒度或介于两者之间的折中方案（比如只按函数签名分组，不分调用点上下文）。

粒度越细，允许的目标越少，攻击者能钻的缝越窄；但实现代价和兼容性代价也越高，所以工业界部署的往往偏粗粒度。

#### 4. 和前面模块的连接

粗粒度 CFI防的住ROP/JOP，防不住coop

协程的 h.resume()：落点是 resume 函数的入口，本身就合法，粗粒度 CFI 放行，但细粒度 CFI 能不能拦住它，取决于防御有没有专门为协程这种"从堆读指针再调用"的模式建模——论文的论点正是现有细粒度方案大多是围绕虚函数调用和传统函数指针设计的，没有把协程 resume/destroy 这条路径纳入保护范围，这是一个新的、没被覆盖的攻击面。

### 第 2 讲 ——Intel CET：IBT 与影子栈

CET（Control-flow Enforcement Technology）是 Intel 把 CFI 思想做进硬件的方案，分两块，分别对应前面讲的两类风险点：间接 call/jmp，和 ret。

#### 1. IBT（Indirect Branch Tracking）—— 管间接 call/jmp 的落点

每一次间接 call 或间接 jmp，落点那条指令必须是 ENDBR64（或 32 位下的 ENDBR32），否则 CPU 直接触发异常，程序崩溃

实现机制:

- 编译器在每一个可能作为间接跳转目标的函数入口，都插入一条 endbr64。
- CPU 内部维护一个状态机，叫 tracker，正常状态是 IDLE。
- 执行一条间接 call/jmp 时，tracker 切到 WAIT_FOR_ENDBRANCH 状态。
- 落点处的下一条指令必须是 endbr64，CPU 看见它就把 tracker 切回 IDLE，放行。如果落点不是 endbr64，tracker 还停在等待状态，CPU 立刻触发 #CP（control protection）异常，程序终止。

而直接call的不会受到IBT 约束，地址是写死的，不是利用指针的地址

IBT 的粒度：它只回答"落点是不是某个函数的入口"，不回答"这个入口该不该在这里被调用"。所以 IBT 本质是粗粒度 CFI 的硬件版——挡得住 JOP（它的 gadget 落在函数中间，没有 endbr64），ROP 靠 ret 串联，归影子栈管，挡不住 COOP（vfgadget 入口本来就有 endbr64），也挡不住协程劫持（resume 函数入口本来就有 endbr64）

#### 2. 影子栈（Shadow Stack）—— 管 ret 的目标

IBT 不管 ret，因为 ret 的目标不是"跳到某个函数入口"，而是"跳回调用者里 call 之后的那一条指令"——这不是函数入口，不可能要求它前面有 endbr64。ret 需要另一套机制，就是影子栈。

机制:

- CPU 维护一块独立于普通数据栈的只读栈，叫影子栈，一般应用代码不可写，只有 call/ret 指令能操作它。
- 执行 call 时，CPU 同时把返回地址压两份：一份压进正常栈（程序能读写的那份，ROP 攻击的目标），一份压进影子栈（受硬件保护，程序写不了）。
- 执行 ret 时，CPU 从正常栈弹出返回地址，同时从影子栈弹出它保存的那份，两者一比对：相等才放行，不相等触发异常终止。

攻击者可以通过栈溢出改掉了正常栈上的返回地址，但是无法改变影子栈里的那份副本

#### 3. 对比影子栈和IBT

| 防护 | 管什么 | 规则 | ROP | COOP | 协程劫持 |
| --- | --- | --- | --- | --- | --- |
| 影子栈 | ret | 栈上地址必须和影子栈副本一致 | 拦住 | 不相关 | 不相关（resume 不是靠 ret 回到调用者,是call） |
| IBT | 间接 call/jmp | 落点必须是 endbr64 | 不相关(gadget本就不走间接跳转) | 放行（落点是合法函数入口） | 放行（resume 函数入口本就有 endbr64） |

**Q1：为什么 IBT 不管 ret，而要单独设计影子栈？**

A1：ret 的目标从来就不是"函数入口"，而是调用者里 call 指令之后的那条指令——那个位置本来就不该有 endbr64（每个 call 之后都要求有，这既不现实也没必要）。所以 IBT 这套"落点必须是 endbr64"的规则对 ret 根本不适用，不是"管不着"，而是"管的对象不一样"。ret返回的要么是正常函数，要么就不是函数，而是gadget

**Q2：综合本模块：如果你是防御设计者，针对协程劫持，你觉得该往 IBT 加什么规则，或者该往影子栈的思路里加什么类似机制？（没有标准答案，说说直觉）**

A2：协程帧也有标识符，以及在协程挂起的时候也放入一个“影子”的地方，resume的时候对照
